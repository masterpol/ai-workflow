# Knowledge Graph

## Purpose

Persistent project memory that grows over time. Unlike session-specific context, knowledge persists across all tasks and can be searched when relevant.

## Structure

```
knowledge/
├── README.md           # This file
├── index.md            # Auto-generated catalog of all knowledge
├── decisions/          # Extracted decision patterns (from ADRs)
├── patterns/           # Learned code patterns
├── entities/           # Key classes, modules, APIs
├── issues/             # Common issues and solutions
├── meta/               # Health tracking and usage metrics
│   └── usage-log.md    # Audit history
└── templates/          # Templates for new knowledge entries
```

## Knowledge Types

### Decisions (`decisions/`)
Technical decisions that affect multiple features. Extracted from ADRs but indexed for quick search.

### Patterns (`patterns/`)
Recurring code patterns discovered during development. "This is how we do X in this project."

### Entities (`entities/`)
Key architectural entities: important classes, modules, APIs, services.

### Issues (`issues/`)
Problems encountered and their solutions. Prevents re-solving the same problems.

## When Knowledge is Created

1. **After `/finish`** — The `/extract` skill runs automatically
2. **After significant decisions** — Manually via `/extract`
3. **After solving a tricky bug** — Add to `issues/`
4. **When establishing patterns** — Add to `patterns/`

## How Knowledge is Used

1. **`/resume`** — Searches knowledge for relevant context
2. **`/request`** — Checks for similar past features
3. **`/design`** — References established patterns
4. **`/impact`** — Surfaces relevant warnings before development
5. **`/develop`** — Looks up known issues
6. **`/search`** — Explicit knowledge search
7. **`/knowledge-health`** — Audits graph for staleness, unused entries, promotion candidates

## Index Format

`index.md` and `graph.json` are both generated by `node ai-framework/scripts/graphify.js` — never
hand-edit either one, edit the entries and re-run the script instead. It runs automatically at
the end of `/setup` (Step 3), `/ship` (after knowledge extraction), and `/cooldown` (after
promotion/archival); run it manually after any other manual edit to an entry.

`graph.json` is the machine-readable form — `nodes[]`, `edges[]` (`related`/`[[wiki-link]]`
references resolved to `{from, to}` pairs by id), and `tagIndex` (tag → node ids). It is what
lets each phase *traverse* the graph — filter by type, walk `related` links, or look up a tag —
instead of re-scanning every markdown file under `knowledge/` on every lookup. `/shape`'s
knowledge gate, `/search`, `/knowledge-health`, and `/cooldown` all read it. Run
`node ai-framework/scripts/graphify.js --check` anytime to validate without writing (flags
broken links, orphans, and duplicate ids; non-zero exit on duplicate ids).

`index.md` is the human-readable rendering of the same data — grouped by type, plus a tag index
and an auto-generated Mermaid graph of the `related` edges:

```markdown
# Knowledge Index

Last updated: 2026-02-28

## Decisions (5 entries)
- [jwt-auth](decisions/jwt-auth.md) — Authentication uses JWT tokens
- [backend-platform-choice](decisions/backend-platform-choice.md) — Chosen backend platform
...

## Patterns (3 entries)
- [container-presentation](patterns/container-presentation.md) — Component split
- [auth-guard-pattern](patterns/auth-guard-pattern.md) — Auth pattern
...

## Entities (4 entries)
- [session-pipeline](entities/session-pipeline.md) — Session runtime flow
...

## Issues (2 entries)
- [hydration-mismatch](issues/hydration-mismatch.md) — SSR issues
...
```

## Entry Format

Each knowledge entry follows:

```markdown
---
id: <unique-id>
type: decision | pattern | entity | issue
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: [tag1, tag2]
related: [other-entry-id]
source: ADR-XXX | feature-name | manual
confidence: low | medium | high
---

# Title

## Summary
One paragraph TL;DR

## Details
Full explanation

## Related
- [[wiki-link-to-related-entry]]

## References
- Link to ADR, design plan, or code
```

### Confidence Levels
- **low**: First observation, single occurrence
- **medium**: Confirmed in 2+ features or validated by review
- **high**: Established, referenced 3+ times, or promoted from issue to rule

### Wiki-Links
Use `[[entry-id]]` to cross-reference entries. This enables:
- Obsidian graph visualization (open `knowledge/` as an Obsidian vault)
- Auto-generated Mermaid knowledge map
- `/knowledge-health` cross-reference validation

## Knowledge Lifecycle

```
Created (low confidence)
  → Referenced in /design or /develop (medium confidence)
    → Validated across 3+ features (high confidence)
      → Issue recurs 2+ times → PROMOTED to rule in rules/

Stale (60+ days, no references)
  → Flagged by /knowledge-health
    → Updated or removed
```

## Auditing

Run `/knowledge-health` every 3-5 features to:
- Detect stale entries (referenced files deleted, 60+ days unused)
- Find unused entries (never referenced in workflows)
- Identify promotion candidates (recurring issues → rules)
- Validate cross-links and tags
- Track trends in `meta/usage-log.md`
