# Pattern: local eval data must be gitignored alongside the dataset specs

## Summary

A project's `.project/evals/` mixes two kinds of content with opposite tracking rules: dataset specs
(`.project/evals/datasets/`, baseline.json) are project records that travel with the repo, while run
artifacts (`.project/evals/runs/`) and the judge response cache (`.project/evals/.cache/`) are local
instance data that must not be committed. A workflow doctor check fails an install whose root
`.gitignore` does not ignore the instance paths.

## The Pattern

- Keep tracked:
  - `.project/evals/datasets/` — golden cases and their schemas; reviewable in PRs.
  - `.project/evals/baseline.json` — pinned judge model + baseline scores; the grader reads it
    to detect `REBASELINE NEEDED`.
- Ignore (instance data, never committed):
  - `.project/evals/runs/` — historical run reports (JSON + Markdown) generated by the grader.
  - `.project/evals/.cache/` — judge response cache keyed by case id.
- The root `.gitignore` of every install must list both ignore rules. `workflow-doctor` enforces
  this with a dedicated `.gitignore (eval data)` check that fails when either rule is missing.
- The pattern matches the existing `.project/metrics/`, `.project/skills/packages/`, and
  `.project/skills/registry.json` conventions: instance data stays in the repo, never in version
  control.

## When to Use

- Adding the eval harness to a new project — seed the `.gitignore` rules in Step 1, before the
  first eval run writes anything under `runs/` or `.cache/`.
- Merging this bundle into a project that already has its own `.gitignore` — copy the two
  eval rules into the project's existing ignore file; do not rely on a merged template.
- A new local-instance directory appears under `.project/` — extend both `.gitignore` and the
  doctor's required-patterns list in the same change.

## When NOT to Use

- The eval dataset specs under `datasets/` — those are tracked on purpose; an untracked dataset
  is a deploy bug, not a privacy win.
- A one-off artifact that is meant to ship (e.g. a published benchmark report) — those go under
  `.project/reports/`, not `.project/evals/runs/`.

## Examples in Codebase

- `.gitignore` — `.project/evals/runs/` and `.project/evals/.cache/`
- `ai-framework/scripts/workflow-doctor.mts` — `checkGitignore()` enforces the two rules
- `ai-framework/scripts/workflow-doctor.test.mts` — fixture seeds the required rules;
  `doctor flags a .gitignore that misses eval runs or cache` proves the failure case
- `ai-framework/rules/eval-harness.md` — directory map marks `.cache/` as "gitignored"
