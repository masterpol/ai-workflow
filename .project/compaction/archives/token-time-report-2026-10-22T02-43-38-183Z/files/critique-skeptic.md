| S1 | skeptic | high | missed-rabbit-hole | `issues/metrics-ancestor-swap-during-async-lease.md`, `issues/hardening-a-shared-reader-made-its-writer-destructive.md` | The pitch names a "single-lease snapshot boundary" and "guarded reader reuse", but not the directory-identity pin. The repo has already been burned here: the usage writer validated `.project/metrics` before awaiting the lease, and a swap to a symlink during the wait made recording and reporting read and write outside state. A report that takes the lease and then reads `token-consumption.json` and `workflow-usage.json` has the same window. Add a rabbit hole: pin the parent and metrics-directory identities (inode, device, canonical path) before the lease wait, and recheck them inside it and before the `.project/metrics/flow-report.*` publish. If flow leaves need a new or extracted guarded reader, that is a tenth or eleventh file. If extraction makes a shared reader stricter, list every caller that writes on "absent" (the data-destroyer issue). |
| S2 | skeptic | high | missed-rabbit-hole | `issues/counting-untrusted-labels-in-a-plain-object-inherits-prototype-keys.md`, `issues/snapshot-metadata-bypassed-output-scrubbing.md` | The pitch has "hostile-label tests" and "nested maps", but the joiner is exactly the case the two earlier issues describe. Pitch, phase and scope labels come from files on disk and are used as map keys. A `{}` map inherits `constructor` or `toString` and drops `__proto__`. The joiner's nested pitch/phase/scope maps and every count table must use `Object.create(null)` or `Map`. The second issue shows that metadata (schema versions, labels, updated times, `state.json` history strings) can reach Markdown and HTML without passing the scrubber. Require that every store-derived string, including source status notes and rejection reasons, goes through scrub-equality or a fixed reason string. Never stringify a rejected value into a note. Add `constructor`, `__proto__` and credential-shaped labels as named regression cases for JSON, Markdown and HTML. |
| S3 | skeptic | medium | missed-rabbit-hole | `workflow-metrics-state.mts` (`LIMITS`, `OTHER` fold), `token-consumption.mts` (`foldPitch`, `leafCount`) | Both stores cap pitches and leaves and fold overflow into `(other)`, but each folds on its own schedule (usage caps at 50 pitches and 600 leaves; the token store has its own `leafCount` and `foldPitch`). The same real pitch can therefore be exact in one store and folded in the other. The joiner would show it as a token-only row plus a timing-only row, which reads as an attribution gap that is really a cap artifact. The pitch's rule that `(other)` never matches is right but does not cover this. Add a rabbit hole: say in the output that unjoined rows may be cap folds, show each store's `(other)` totals beside the unjoinable counts, and add a fixture where one store folds a pitch and the other does not. Live data has "6 over cap" intervals, so this is real, though the stores are sparse today. |

## Budget

The projected 9 files and 1,500 LOC cap are plausible but tight. The joiner, renderer for three formats, hostile-label cases, lease/swap tests and the `/state` link are the bulk of it. S1 may add one extraction module (file 10), still within the 15-file cap. LOC risk is in the two test files and the HTML renderer. If both are written in full they may approach 1,500 on their own, so the plan should hold the split condition the pitch already names for the report scope.

## Not proposed

Fabricated efficiency ratios, estimated tokens and unavailable flow components are already covered as no-gos. Overlap with `workflow-v3-rollout` is checked in the evidence file and is outside this role.
