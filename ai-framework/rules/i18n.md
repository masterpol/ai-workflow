# Internationalization (i18n) Rules

Only applies if your project ships user-facing copy in more than one language. If it doesn't,
skip this file — or delete it once `/setup` confirms your project is single-locale.

## Scope

These rules apply to all user-facing copy across every client surface (web, mobile, etc.), plus
AI-generated default-language behavior if your product generates natural-language output.

## Locale Strategy

- Define your supported locale list explicitly (e.g. `en`, `es`) — don't leave it implicit.
- Decide and document your locale-resolution order (e.g. explicit user preference → device/browser
  language → default locale).
- Every touched feature must ship strings for all supported locales in the same change — no
  locale left behind for a follow-up PR.

## Message File Structure

- Each client surface keeps its own message catalog (e.g. `<web-workspace>/messages/<locale>.json`,
  `<mobile-workspace>/i18n/<locale>.json`) — record your project's actual paths in
  `.project/context/stack.md` once `/setup` detects them.
- Use top-level namespaces by domain/feature, not by page URL (e.g. `common`, `navigation`,
  `settings`, `errors`, plus your product's own feature namespaces).
- Namespace keys must not contain dots.

## Key Design

- Use stable semantic keys, not source-language strings as keys.
- Prefer full-sentence messages with placeholders over concatenated fragments.
- Keep key names consistent between locales.
- Avoid renaming keys unless required; key churn breaks downstream usages and translator memory.

## Plurals and Variable Messages

- Use ICU-style plural/select message patterns whenever quantity or grammatical variants are
  needed.
- Every plural message must include an `other` branch.
- Do not implement custom plural logic in app code — use your i18n library's or
  `Intl.PluralRules`' formatter support.

## AI Language Behavior (if applicable)

If your product generates AI text output for end users:
- Default to the user's preferred language setting, falling back to your default locale.
- If the content is scoped to some other language-bearing context (a document, a conversation, a
  workspace with its own language setting), that context's language should take precedence over
  the user's general preference — record the actual precedence rule for your domain once decided.

## Hardcoded Copy Policy

- Do not introduce new hardcoded user-facing strings in components or routes.
- If touching a file with hardcoded copy, migrate that touched copy to translation keys.
- Exceptions are only for non-user-facing logs, internal telemetry, and test-only fixtures.

## Validation and CI

- Run an i18n key-parity check locally and in CI (generate this via `/setup` or your own tooling
  once the message-catalog format is known). It should enforce:
  - key parity across all supported locales
  - namespace consistency
  - plural-object shape consistency and required `other` branch
- Lint and test gates still apply on top of this.

## Translator Workflow

- Write source-language messages first, then mirror them into every other supported locale in the
  same change.
- Keep interpolation variables identical across locales.
- Prefer translator comments in code when context is ambiguous.
