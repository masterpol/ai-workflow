# /ui-design — UI Generation

> **Recommended capability profile:** `standard` for visual and layout reasoning. Select an available model using `ai-framework/integrations/harnesses.md`.

You are in the **UI DESIGN** phase.

## Your Goal
Generate a production-ready UI component skeleton for a feature or screen — respecting boundaries, design system, accessibility, and i18n from the start.

## Context Budget
~6K tokens:
- Feature requirement or description
- `ai-framework/rules/component-architecture.md`
- Your project's frontend-framework rule (generated by `/setup`, if one exists)
- `ai-framework/rules/boundaries.md`
- `ai-framework/rules/i18n.md` (if the project is multi-locale)
- `.project/design/ux/design-system.md` (if present)
- Existing similar components (1–2 examples for pattern reference)

## Steps

### 1. Understand the UI requirement
- What screen / feature is being built?
- What user interactions are needed?
- Is this a new page, a component in an existing page, or a modal/drawer?

### 2. Load design rules
Read:
- `component-architecture.md` — layer placement (feature vs shared vs ui)
- Your project's frontend-framework rule, if `/setup` generated one — rendering-mode decision
  (server vs client, static vs dynamic, whatever your framework's equivalent split is)
- `boundaries.md` — where this component lives
- `i18n.md` — string key format (skip if the project is single-locale)
- `design-system.md` (if available) — colors, typography, spacing tokens

### 3. Design component hierarchy
Determine:
- Which components are needed (list them)
- Which layer each belongs to (feature / shared / ui)
- Rendering mode for each, if your framework distinguishes one (e.g. server vs client component)
- Props interface for each (with types)
- Estimated line count (must be ≤ 150 per component)

If a component would exceed 150 lines, split it now — not after building it.

### 4. ASCII wireframe (for complex layouts)
Draw a simple layout sketch:
```
┌─ Page ─────────────────────────────────┐
│ ┌─ Header ──────────────────────────┐  │
│ │ [Title]              [Button]     │  │
│ └───────────────────────────────────┘  │
│ ┌─ Content ─────────────────────────┐  │
│ │ ┌─ Card ──┐  ┌─ Card ──┐         │  │
│ │ │         │  │         │         │  │
│ │ └─────────┘  └─────────┘         │  │
│ └───────────────────────────────────┘  │
└────────────────────────────────────────┘
```

### 5. Generate component skeletons
For each component:
- Correct file path (following boundaries)
- Typed props interface
- Reuse of existing UI primitives/component library where applicable — don't invent new ones the
  project already has
- Styling per your project's actual system (utility classes, CSS modules, styled-components,
  etc. — check `.project/context/stack.md`), mobile-first if the product needs it
- ARIA labels and semantic HTML baked in
- i18n key stubs for ALL user-facing strings if the project is multi-locale (no hardcoded text)
- Loading / empty / error states stubbed

### 6. Generate i18n key list (if applicable)
List all new keys needed, one entry per supported locale's message catalog.

### 7. Self-validate each generated file
Read each generated file against the rules and confirm: correct layer placement, no cross-feature imports, under 150 lines, no hardcoded strings, ARIA labels on interactive elements. Fix any issues flagged before presenting to user.

### 8. Present for approval
Show:
- Component hierarchy with file paths and line estimates
- ASCII wireframe (if drawn)
- Architectural decisions made (why server vs client, why feature vs shared)
- i18n keys needed
- Any concerns or trade-offs

## Output Format

```markdown
## UI Design: [Feature Name]

### Component Hierarchy
- `components/features/[domain]/[ComponentName]` (~80 lines) — [purpose]
  - Props: `{ items: Item[], onSelect: (id: string) => void }`
- `components/features/[domain]/[SubComponent]` (~60 lines) — [purpose]
- `components/shared/[SharedComponent]` (~40 lines) — [only if 2+ features need it]

Note the rendering mode per component only if your framework distinguishes one (e.g. server vs
client component).

### Wireframe
[ASCII layout]

### i18n Keys Required (skip if single-locale)
```json
{
  "FeatureName": {
    "title": "...",
    "emptyState": "...",
    "errorState": "..."
  }
}
```

### Architectural Decisions
- [Decision]: [Rationale]

### Files to Create
1. `path/to/Component.<ext>`
2. `path/to/SubComponent.<ext>`

### Next Steps
Attach these skeletons to the UI scope in `plan.md` and proceed, or adjust the hierarchy first.
```

## Confirmation Gate

After presenting the design:
1. ✓ **Approve** — attach to the UI scope in `plan.md`
2. ↻ **Revise** — adjust hierarchy or wireframe
3. ✕ **Stop** — pause here

**Do not start building the UI scope until approved.**

## What's Next
After approval, `/build` uses these skeletons as the starting point for the UI scope. The finished UI is scored by the `ux-reviewer` subagent during `/audit`.
